# Project architecture rules

- Resolve update destinations from persisted entity and parent slugs during the signed-in existing-review lookup, and consume one-time modal navigation state on the destination; this avoids intermediate ID/query URLs without changing durable deep links.
- Review and timeline-update Mux videos are validated, made trustworthy and linked by database triggers inside the same save, and only the trusted-server patch may write Mux state; this removes the two-step registration failure window posts have and keeps client-supplied playback data out.- Review composers send kept saved videos back exactly as loaded and new videos with identity fields only, upload videos through Mux only (no storage fallback), and treat the review-video setting as gating new picks only; this keeps trusted Mux state server-owned and makes switching the setting off never alter saved videos.
- Review/timeline media is drawn only through `ReviewMediaBlock` + `visibleReviewMedia` (stable ids, owner/edit-window display rule); saved videos track with explicit review/update context, while composer previews do not, keeping attribution and Post analytics separate.
- Review display projections retain the original saved media ID in UI-only `viewMediaId`; card and lightbox tracking use that value, not the namespaced display key, so server matching stays authoritative without changing playback identity.
- The entity page has exactly one `FeedVideoManagerProvider` (top of `EntityV4`) covering reviews, posts and the timeline viewer; nested managers would isolate players and break one-at-a-time playback.
- Review composers pass `unknownDurationAllowed` to `validateMediaFile`: an unmeasurable length is an explicit allowed state and the server's Mux duration decides; posts keep the old check until a separate decision.
- Post Mux fields are rebuilt server-side by `post_mux_truth_item` on every save and trusted patch, and unchanged existing videos pass through byte-identical; one rebuild keeps client data out and protects historical posts.
- New/replacement Mux videos use shared composer-only readiness rules (owner status plus server duration) before publishing; saved content is reread after existing linking without reinserting on refresh failure, so immediate playback never trusts local previews or weakens server validation.
- Managed feed videos attach HLS only inside the provider's separate loading budget (`feedVideoLoadBudget`, keyed by stable slot id, pins > active > grace > nearest); playback selection stays solely in FeedVideoManager so bandwidth limits never change autoplay.
