# Ready-before-publish videos: final plan

## Verified findings
- The reported Post (`89e2af5f-ac2e-4eef-83a5-e671a0628b06`) was saved at 08:34:16 UTC. Mux reported Ready at approximately 08:34:29; its saved media was patched to Ready at 08:34:30. It is now linked and playable. This was real processing, not a missing link.
- Phase 2 deliberately clears playable addresses and thumbnails while a Post video is processing. The former saved preview cannot be restored by trusting a client-supplied video address.
- The home feed subscribes to Post inserts, not updates. A processing item already fetched into the feed therefore does not refresh from that subscription when its saved media becomes Ready.
- The Post composer has a local video preview. New review and timeline composers currently leave after a successful save without a readiness wait. The timeline preview hook loads updates once per review-list change.

## Intended experience
Finish both uploading and Mux processing **before a newly added or replacement Mux video can be published**. Apply this to Posts and the new Review / Timeline Update pages, including their edit modes.

Preserve the current local video preview inside the composer wherever it is already available; do not hide it or delay it until processing finishes. Other upload stages retain their existing still preview. Authors can continue writing and choosing subjects/tags while upload and processing run. Once Mux confirms a valid, playable video, switch the composer preview to the normal Mux player and enable publishing. Save then redirects normally—no routine post-save wait and no temporary local video carried into the feed.

This is preferable to the temporary-feed-preview approach: it is simpler, lets the author preview the processed video before publishing, and avoids a local-to-Mux player handoff. The tradeoff is a longer preparation stage before publishing.

## Changes
1. Reuse the existing uploader and owner-facing Mux status hook. Upload starts on selection; processing follows Mux's own lifecycle, never waits for Post/Save. Separate **Uploading X% → Processing video… → Ready** explicitly. Transfer percentage reflects bytes uploaded; processing has an indeterminate finishing indicator, not an invented encoding percentage. Use the existing skeleton/loading conventions rather than adding a generic spinner.
2. Preserve composer-only local playback while processing, clearly marked as a preview—not proof of readiness. Once Ready, preview the actual Mux video using the existing shared player. Restarting from the beginning is acceptable; preserve shared mute naturally, but add no exact-position handoff state or acceptance requirement. Extend the owner status read with server-measured duration; require Ready, asset ID, playback ID, and a finite positive duration no greater than 60 seconds for newly added/replacement videos. Unknown/not-yet-returned server duration stays pending, and a new video over 60 seconds is refused even if Mux calls its asset Ready. Backend validation remains the final authority.
3. Block Post/Review/Timeline final save while a **new or replacement video** is uploading, processing, unverified, or failed, with clear state-specific copy. Enforce this in submit handlers, keyboard/form submissions, and button states. Gate any Next action that actually submits content; keep non-submitting steps and ordinary composing available. Photos, text-only saves, unchanged saved videos, and existing stored-file upload behavior retain their current rules. Existing broken videos do not suddenly prevent unrelated permitted edits.
4. Handle failure, long processing, offline/reconnect, cancellation, and replacement safely. Keep remove/cancel available; explain prolonged processing and allow status retry or removing the video to publish without it. Never auto-publish, pretend Ready, abandon the draft, delete a Mux asset, or resurrect a cancelled selection after a late status event. Preserve admitted uploads if the Review-video switch changes mid-session.
5. Save once and use freshly persisted media at the destination. Where Post linking patches media after the initial insert response, reread the saved Post after the existing linking step rather than seeding the feed with the stale insert result. Reviews and updates likewise refresh only their relevant destination content/cache. Preserve the saved content ID before linking/refresh work: a successful save must never become a failed save because those later steps fail. Offer reconciliation/status recheck for that same ID, not another insert. Do not navigate to a playable-looking item based only on local status.
6. Keep existing viewer Processing/Unavailable tiles unchanged. **Defer broad viewer auto-refresh/polling across Home, Reviews and Timeline.** Add no such machinery here unless strictly required to deliver freshly saved content on its immediate destination; any independently observed legacy/recovery refresh gap remains a separate follow-up.
7. Test every affected create/edit mode: uploading/processing blocks, Ready unlocks and previews Mux, failure/removal/replacement, missing status/duration, server duration rejection, cancellation and late events, offline/retry, switch-off mid-session, mixed media, and unchanged saved-video edits. Include linking/refresh failure after a successful save with no duplicate content, and processing completion after edit expiry with no window extension. Verify immediate destination playback after a Ready save and existing player/lightbox coordination.

## Technical safeguards
- Read trusted **content-level** media: an upload can be Ready while the saved content correctly rejects its duration. Never override that rejection with `mux_uploads` playback fields.
- Timed refresh uses visibility/online-guarded `setTimeout`, cancels on unmount, and is bounded. Background read failures stay silent; existing access controls remain authoritative.
- Keep local preview URLs only for their composer lifetime, revoking them on removal/replacement/unmount; never persist blob URLs or insert them into feed caches. No temporary video playback registry or navigation handoff is needed.
- Refresh the relevant content/cache before navigation, including when Mux was already Ready before saving.
- Scope successful-save refreshes by content identity. Keep stable player identities and avoid remounting unrelated players, resetting scroll/lightbox state, or adding extra view counts. Do not redesign tracking.
- Processing never extends an edit's one-hour eligibility. On server-authoritative expiry rejection, retain the draft and use the existing expiry outcome; do not bypass the rule or convert the edit to a new entry automatically.
- Add focused status-hook tests for duration-only updates, a delayed initial read after a newer realtime event, reconnect/status recheck, and selection cancellation. Older responses must not regress readiness or unlock a removed/replaced upload. Reuse the owner-facing hook, not a second video-status system.
- No new SQL rules, mapping redesign, upload fallback, analytics changes, or Phase 3 work. Retain server-owned Mux fields, duration/ownership checks, one-hour policy, visibility rules, and current media ordering.
- Leave both excluded historical Posts untouched and unlinked. Leave old stored-file videos, legacy review popups, Mux assets, and the Review-video switch untouched.

## Contract change and Phase 3 boundary
- This intentionally replaces the earlier composer contract that allowed saving a newly uploaded video while Processing. Update the affected contract documentation and tests; record the task in the roadmap when implementation begins. The previously frozen `/create` behavior changes only in readiness gating, truthful stage display, and the local-to-streaming composer preview transition.
- This is an application publishing gate, not a new database prohibition against Processing saves. Older clients and race/recovery cases may still produce Processing content; retain the neutral viewer tile and all server truth protections.
- Ready-before-publish does **not** replace Phase 3 atomic Post save/mapping. The current second-step linking can still fail after the Post is saved, even for a Ready upload. Keep the existing registration/retry flow, reread its saved result, and surface a saved-but-link-pending outcome without duplicate Posts if necessary; never fake successful playback. Atomic/idempotent linking remains separate Phase 3 work.
- Historical data protections and the previously unverified Phase 1 simultaneous overlap remain unchanged. This UX work does not close either outstanding verification item.
